# Frontend трекера питания

Создан: 1 ноября 2026 года. Обновлён: 7 ноября 2026 года.

Документ описывает рабочий стек и архитектуру первой версии frontend. Приложение пока не инициализировано: это техническая основа для последующей реализации.

## 1. Назначение и границы первой версии

Адаптивное веб-приложение для работы с продуктами, рецептами, личным расписанием, дневником и целями КБЖУ. Основные сценарии должны быть удобны на компьютере и телефоне.

Этот README описывает только frontend: стек, структуру кода, интерфейс, клиентское состояние, работу с API и проверки UI. Источник истины для скоупа, сущностей, бизнес-правил, расчётов и доступа — [backend/README.md](../backend/README.md). При изменении предметного правила сначала обновляем backend-документ; здесь меняем только зависимое поведение клиента и ссылки.

- Состав MVP и будущие этапы: [задачи и этапы backend](../backend/README.md#1-задачи-и-этапы).
- Правила учёта съеденного: [дневник и подтверждение питания](../backend/README.md#11-дневник-и-подтверждение-питания).
- Критерии функциональной готовности: [готовность первой версии](../backend/README.md#готовность-первой-версии).

Авторизация — отдельный блок клиентской реализации и приёмки. Требования сервера находятся в [разделе авторизации](../backend/README.md#17-авторизация-и-доступ), клиентское поведение — в разделе 8 ниже. Наполнение каталога уточняем по ходу разработки.

## 2. Стек технологий

### Рабочая основа

| Задача | Технология | Назначение |
|---|---|---|
| Интерфейс | React | Компоненты и взаимодействие с пользователем |
| Язык | TypeScript в strict-режиме | Типизация данных, компонентов и API-контрактов |
| Сборка | Vite | Локальная разработка и сборка SPA |
| Маршрутизация | React Router | Страницы, параметры маршрутов и URL-фильтры |
| Общее клиентское состояние | Redux Toolkit + React Redux | Настройки и состояние общих клиентских сценариев |
| Серверные данные | RTK Query | Запросы, мутации, кеширование и инвалидация |
| UI | Material UI (`@mui/material`) | Поля, кнопки, карточки, диалоги, навигация и layout |
| Стили компонентов | MUI theme, `sx`, `styled` | Единое оформление и локальная кастомизация |
| Управление формами | React Hook Form | Состояние формы, ошибки, динамические списки полей |
| Проверка форм | Zod | Схемы и проверка значений формы |
| Тестирование | Vitest | Модульные и компонентные тесты |
| Подмена API в development | MSW | Моковые ответы backend для разработки интерфейса |
| Архитектура | Feature-Sliced Design (FSD) | Слои, слайсы, сегменты и явные границы зависимостей |

React + Redux — исходное пожелание пользователя. MUI, React Hook Form, Zod, Vitest, MSW и FSD явно выбраны пользователем. Остальные пункты — рабочая основа из обсуждения.

### Backend и границы frontend

Frontend получает JSON по HTTP от REST API. Серверный стек, сущности, транзакции, проверки доступа и расчёты определены в [архитектуре backend](../backend/README.md#4-архитектура-приложения) и [согласованном стеке](../backend/README.md#2-согласованный-стек).

Клиент отвечает за отображение и ввод. Предварительный расчёт черновика даёт обратную связь в форме; сохранённые итоги отображаем из API по [правилам расчёта backend](../backend/README.md#12-расчёты-кбжу).

### Дополнительные инструменты

| Задача | Инструмент | Статус |
|---|---|---|
| Работа с React-компонентами в тестах | React Testing Library | Предлагаемый вспомогательный инструмент для Vitest |

Сквозные (E2E) тесты в приложении не пишем. Инструменты для них в стек не включаем.

Версии пакетов и совместимые зависимости нужно зафиксировать при инициализации приложения в lock-файле. Номера версий этот документ не задаёт.

## 3. Архитектура Feature-Sliced Design

Клиентское SPA с отдельным REST API. Границы ответственности заданы в [архитектуре backend](../backend/README.md#4-архитектура-приложения); здесь описана организация клиентского кода.

Используем FSD: код разделяется на слои, внутри предметных слоёв — на слайсы, внутри слайсов — на технические сегменты (`ui`, `model`, `api`, `lib`, `config` по необходимости). Исходная схема была приближена к FSD; здесь явно разделяем бизнес-сущности, пользовательские действия и самостоятельные блоки интерфейса.

Порядок слоёв сверху вниз: `app → pages → widgets → features → entities → shared`. Создаём только нужные слои и слайсы, без пустых заготовок.

```text
frontend/
  src/
    app/
      providers/             # MUI, Redux и остальные провайдеры
      router/                # Маршруты и layout приложения
      store/                 # Настройка Redux store
      theme/                 # Тема MUI и настройки компонентов
      mocks/                 # Запуск MSW и сборка обработчиков

    pages/
      auth/                  # Отдельный блок экранов авторизации
      recipes/
      recipe-editor/
      products/              # Личные и публичные продукты
      meal-plan/
      diary/
      settings/

    widgets/                 # Крупные самостоятельные блоки, когда нужны
      meal-plan-calendar/
      daily-nutrition-summary/

    features/                # Пользовательские действия
      create-recipe/
        model/               # Схема Zod и логика формы
        ui/                  # Форма React Hook Form
        index.ts             # Публичный API слайса
      edit-recipe/           # Автор обновляет текущий Recipe с тем же ID
      create-product/        # Общий сценарий пользователя и администратора
      edit-product/          # Исправление текущей карточки с сохранением ID
      publish-product/       # Только ADMIN для собственных карточек
      quick-add-product/
      confirm-consumption/
      add-meal-entry/
      move-meal-entry/
      adjust-consumption/
      adjust-consumed-nutrition/ # КБЖУ только выбранной съеденной записи
      skip-meal/
      edit-nutrition-goal/

    entities/                # Бизнес-сущности
      recipe/
        api/                 # Запросы и преобразования данных рецепта
        model/               # Модель и вычисления сущности
        ui/                  # RecipeCard и другие представления
        index.ts             # Публичный API слайса
      ingredient/
      meal-plan/
      meal-entry/
      nutrition-goal/

    shared/
      api/                   # Базовый RTK Query API и типы ошибок
        generated/           # Сгенерированные API-контракты, когда появится OpenAPI
      ui/                    # Общие элементы без привязки к одной области
      lib/                   # Форматирование, работа с датами и числами

    main.tsx
```

Это целевая схема. Каждый слайс в `pages`, `widgets`, `features`, `entities` при необходимости содержит свои сегменты и публичный API. `app` и `shared` делятся непосредственно на сегменты, без предметных слайсов.

### Правила зависимостей

- Слайс может импортировать другие слайсы только с нижележащих слоёв.
- Слайсы одного слоя не импортируют друг друга. Их взаимодействие собираем выше: в feature, widget или page в зависимости от задачи.
- Внешние потребители используют публичный API слайса (`index.ts`), без импорта его внутренних файлов.
- Внутри слайса используем прямые относительные импорты, чтобы не создавать циклы через собственный публичный API.
- `app` связывает приложение, провайдеры и маршрутизацию.
- `pages` собирают экраны. Уникальный блок страницы можно оставить внутри неё.
- `widgets` объединяют сущности и действия в самостоятельные блоки интерфейса.
- `features` описывают действия: создать блюдо на основе существующего, изменить собственный рецепт, создать/исправить продукт, опубликовать собственный продукт при роли `ADMIN`, подтвердить еду, добавить или перенести блюдо, скорректировать количество или КБЖУ съеденного, пропустить приём.
- `entities` содержат модели, API и представления бизнес-сущностей.
- `shared` содержит общую инфраструктуру и UI без бизнес-логики питания; он не импортирует верхние слои.
- Предметная специфичность определяет место кода. Не переносим его в `shared` только ради обхода правил импорта.

Пример: `entities/recipe` предоставляет карточку и данные рецепта, `features/create-recipe` — создание нового блюда, в том числе на основе существующего, `pages/recipe-editor` собирает экран. Кнопки действий можно передавать в карточку через props: сущность не импортирует feature.

Базовый RTK Query API находится в `shared/api`. Запросы сущностей подключаются в `entities/*/api`; запросы, относящиеся к конкретному пользовательскому действию, могут находиться в `features/*/api`. Один endpoint не дублируем в нескольких слайсах.

## 4. Где хранится состояние

| Данные | Место хранения |
|---|---|
| Рецепты, продукты, план, дневник и серверные итоги | Кеш RTK Query |
| Черновик нового блюда, копии или авторского редактирования существующего | Состояние формы; режим сохранения и исходная revision задаются явно |
| Открытый диалог, локальное раскрытие карточки | Локальное состояние React |
| Выбранная неделя или дата, поисковая строка, фильтры | URL, если состояние полезно сохранять при переходе или обновлении страницы |
| Общие клиентские настройки, нужные разным экранам | Redux slices при необходимости |
| Предварительное КБЖУ черновика | Вычисление из полей формы |

Не копируем ответы RTK Query в отдельные Redux slices. Не храним вычисляемые итоги как независимое изменяемое состояние. Не сохраняем весь Redux store в `localStorage`.

Настройки отображения можно сохранять отдельно. Сохранение черновиков между перезагрузками — дополнительный сценарий, который требует отдельного решения.

## 5. MUI и оформление

Основной UI-набор — MUI. Вторую библиотеку готовых компонентов в первой версии не добавляем без конкретной необходимости.

- В `app/theme` определяем палитру, типографику, отступы, скругления и общие настройки компонентов.
- Повторяющиеся настройки полей, кнопок и карточек задаём через тему и `components` overrides.
- `sx` используем для локальных изменений и компоновки.
- `styled` используем для повторяемых оформленных компонентов, когда это упрощает код.
- Общую тему создаём централизованно, без независимых палитр внутри функциональных модулей.
- Не оборачиваем каждый компонент MUI автоматически. Обёртка нужна, когда она добавляет поведение или закрепляет соглашение проекта.
- Учитываем клавиатурное управление, видимый фокус, подписи полей, ошибки и контраст.

MUI даёт основу Material Design; внешний вид приложения уточняется собственной темой.

Для первой версии достаточно стандартных компонентов MUI. MUI X рассматриваем отдельно, если появится конкретная потребность в таблицах, графиках или выборе дат. Часть возможностей MUI X имеет коммерческую лицензию; обычное расписание питания не требует покупки этих компонентов.

## 6. Основные экраны и компоненты

### Продукты

Поиск с небольшой задержкой, загрузка результатов частями, карточка и общая форма создания/исправления. Форма показывает поля, ошибки и происхождение данных; доступные действия публикации отображаются по данным о пользователе и карточке.

Видимость, происхождение и разрешённые операции определяет [модель Ingredient](../backend/README.md#ingredient-продукт-пользователя-или-администратора), запросы — [API справочника](../backend/README.md#справочник-и-рецепты). Магазинные источники добавляем в интерфейс на соответствующем этапе из [скоупа backend](../backend/README.md#1-задачи-и-этапы).

### Каталог и редактор блюд

Каталог: поиск, загрузка частями, RecipeCard с названием, выходом и КБЖУ на порцию, переходы к карточке и редактору. Простые блюда отображаются отдельным фильтром по [правилам быстрого добавления](../backend/README.md#быстрое-добавление-продукта--mvp).

Редактор: название, инструкция, состав, граммовки, порции выхода и необязательный готовый вес. Строки формы строим через useFieldArray, валидацию — через Zod и zodResolver. Разделитель дробей нормализуем; пустое значение не превращаем в ноль. Формат API определён в [соглашениях backend](../backend/README.md#5-соглашения-данных-и-времени).

Режимы «Создать», «Создать на основе» и «Изменить» явно различаются в заголовке и действии сохранения. Перед сохранением показываем последствия изменения по [правилам Recipe](../backend/README.md#recipe-сохранённое-определение-и-актуальное-кбжу-без-версий). Разрешённые поля и revision получаем из [контракта рецептов](../backend/README.md#справочник-и-рецепты).

### Быстрое добавление продукта

Компактная форма: выбор продукта, граммы и фактическое время, кнопка «Сохранить съеденное». Полный редактор рецепта в этом сценарии не открывается. Если продукт не найден, даём перейти к его созданию и вернуться к вводу еды. Серверное создание и подтверждение описаны в [быстром добавлении](../backend/README.md#быстрое-добавление-продукта--mvp).

### План питания

На компьютере показываем недельную сетку, на телефоне — выбранный день и вертикальный список. В карточке разделяем блок плана и блок съеденного по данным API. Для действий используем диалоги с понятными полями и состоянием сохранения.

Перенос выполняется действием «Перенести», drag-and-drop отложен. Подтверждение доступно на карточке каждого блюда. Неподтверждённый прошедший план остаётся визуально ожидающим действия; клиент не меняет его на съеденное по часам. Состояния и последствия переноса, пропуска и удаления берём из [правил MealEntry](../backend/README.md#10-личный-план-и-единая-запись-питания).

### Дневник и подтверждение

Карточка позволяет подтвердить блюдо, указать «Уже съел», изменить фактические время/количество, исправить КБЖУ съеденного и отменить подтверждение. В форме пользователь видит, какое блюдо и количество сохраняет. Ручной ввод завершается действием «Сохранить съеденное» без дополнительного шага подтверждения.

Итоги и отметки отображаем по серверному ответу согласно [правилам дневника](../backend/README.md#11-дневник-и-подтверждение-питания). Поля plannedNutrition и consumedNutrition используем в соответствующих блоках карточки по [DTO записей питания](../backend/README.md#личный-план-и-записи-питания). Исторические значения не вычисляем из текущей карточки рецепта.

Если API не допускает граммы, показываем объяснение и ввод порций по [правилам количества](../backend/README.md#количество-и-подтверждение). Перед отменой подтверждения объясняем, какие данные будут удалены, по [правилам отмены](../backend/README.md#копирование-перенос-пропуск-и-отмена-подтверждения). Неподтверждённой карточке не предлагаем корректировку КБЖУ съеденного.

### Цели КБЖУ

В настройках показываем периоды и форму редактирования. При изменении общей границы визуально показываем оба затронутых интервала, серверные ошибки привязываем к полям. Правила периодов и результата изменения — в [NutritionGoal](../backend/README.md#8-цели-nutritiongoal).

## 8. Взаимодействие с API

Маршруты, DTO и семантика операций определены в [REST API backend](../backend/README.md#13-проект-rest-api). Базовый адрес задаём через конфигурацию, без URL в компонентах. Локальное подключение через Vite proxy или CORS согласуем с сервером.

Один createApi находится в shared/api; endpoint областей подключаются через injectEndpoints. Для стандартных JSON-запросов используем fetchBaseQuery. Endpoint не дублируем в разных слайсах. Generated-код расширяем через отдельные адаптеры.

### Простой кеш на N секунд

Следуем [политике свежести backend](../backend/README.md#простое-кеширование-mvp). Значение N выносим в настройку клиента; конкретное число выберем при реализации.

- Отсчитываем N секунд от последнего успешного ответа конкретного запроса.
- При открытии экрана, возвращении в приложение и восстановлении соединения проверяем возраст данных: до истечения N используем кеш, после — запрашиваем заново.
- Само истечение N не запускает постоянный фоновый опрос; свежесть проверяется при следующем обращении к данным.
- После своей успешной мутации используем её ответ и при необходимости повторно запрашиваем данные текущего экрана. Не строим граф зависимостей между всеми продуктами, рецептами и неделями.
- Ключ кеша учитывает endpoint, параметры и пользователя. При завершении сессии очищаем персональный кеш.
- Удаление кеша не удаляет сохранённые на сервере записи или снимки.

В RTK Query keepUnusedDataFor задаёт срок хранения после исчезновения подписчиков. Его можно установить в N, но он не заменяет проверку возраста ответа активного запроса. Для проверки при обращении используем fulfilledTimeStamp и повторный запрос либо эквивалентную настройку refetchOnMountOrArgChange. Общую логику держим в API-слое, а не в каждой карточке.

Не добавляем таймер начисления еды, зависимости от всех связанных revision и WebSocket. Постоянное обновление уже открытого экрана без действий пользователя пока не требуется.

### Мутации и ошибки

На время сохранения блокируем повторную отправку соответствующей формы и показываем загрузку. После ответа отображаем серверные значения. Сложные оптимистические изменения откладываем.

Revision и Idempotency-Key передаём по [транзакционному контракту](../backend/README.md#15-транзакции-и-защита-от-повторов). Формат и статусы ошибок — в [ошибках API](../backend/README.md#ошибки-api). Преобразование ошибок полей в React Hook Form выполняем в API-адаптерах; конфликт показывает пользователю необходимость загрузить актуальные данные, без молчаливого перезаписывания.

Обрабатываем загрузку, пустой результат, ошибки полей, отсутствие доступа, сетевую ошибку и конфликт. Числа и даты преобразуем в одном месте по [соглашениям backend](../backend/README.md#5-соглашения-данных-и-времени).

### Авторизация — отдельный блок

Серверные сценарии, токены, cookie, CSRF и сроки определены только в [разделе авторизации backend](../backend/README.md#17-авторизация-и-доступ). Клиент реализует:

- Экраны регистрации, кода подтверждения, входа и восстановления пароля; переходы по результатам API, ошибки и таймеры из серверных данных.
- Хранение access и CSRF в памяти; добавление нужных заголовков и credentials в общем API-адаптере. Пароли и коды не сохраняем между запусками.
- Начальное восстановление сессии до персональных запросов. До результата показываем загрузку, без преждевременного перехода на вход.
- Одно обновление access для параллельных 401 и не более одного повтора исходного запроса; auth-запросы не вызывают рекурсивный refresh. 403 отображается как отказ доступа.
- Координацию refresh между вкладками; конкретный механизм выбираем при реализации по [жизненному циклу токенов](../backend/README.md#jwt-и-жизненный-цикл-токенов).
- Очистку access, пользователя и персонального кеша при окончательном отказе или выходе. При сетевой ошибке выхода показываем неопределённость серверного отзыва согласно [контракту auth](../backend/README.md#маршруты-auth).
- Видимость действий по данным профиля; серверный отказ обрабатываем независимо от скрытия кнопки.

Этот блок проверяем отдельно от форм и расчётов питания.

## 9. API-контракты и проверки

Источник спецификации и порядок изменения контракта заданы в [контрактах backend](../backend/README.md#14-контракты-и-кеширование). Клиентские типы получаем из OpenAPI; endpoint RTK Query при удобстве генерируем через @rtk-query/codegen-openapi. Ручку подключаем по [общему порядку разработки](../README.md#порядок-разработки).

- Generated-код не редактируем вручную; дополнительное поведение находится в расширении API.
- ORM-модели backend в клиент не импортируем.
- Значения формы могут отличаться от DTO: преобразование выполняем явно.
- Zod проверяет значения формы. Генерация TypeScript-типов не создаёт Zod-схемы и не проверяет произвольные ответы во время выполнения.
- Backend отвечает за итоговые значения; клиентские вычисления дают только предварительную обратную связь в редакторе.
- Форматирование КБЖУ и предварительные расчёты следуют [правилам округления и суммирования backend](../backend/README.md#округление-и-суммирование-кбжу).

### Будущий мобильный клиент

Мобильный интерфейс не входит в текущую реализацию. Общий API предусмотрен [архитектурой backend](../backend/README.md#4-архитектура-приложения). React Native + Expo обсуждался, но окончательно не выбран. При таком выборе можно переиспользовать контракты, схемы форм и чистые функции без браузерных зависимостей; компоненты MUI остаются веб-интерфейсом. Хранение и транспорт токенов определяются на мобильном этапе по [серверным требованиям](../backend/README.md#jwt-и-жизненный-цикл-токенов).

### Подмена API через MSW в development

MSW (Mock Service Worker) — выбранный инструмент для подмены API в development. Он перехватывает HTTP-запросы и возвращает заранее описанные моковые ответы backend. В браузере используется Service Worker. Отдельный backend-процесс для таких ответов запускать не требуется.

Обработчики имитируют ответы FastAPI. При отключении подмены те же запросы RTK Query уходят на реальный backend.

```text
Без подмены: компонент → RTK Query → backend → ответ
С MSW:      компонент → RTK Query → обработчик MSW → тестовый ответ
```

Основная разработка экранов идёт на готовых ручках backend. MSW используем по уже согласованному контракту, чтобы воспроизводить пустые ответы, задержки, ошибки доступа и ошибки сервера. При необходимости те же обработчики можно использовать в тестах Vitest.

Правила использования:

- запуск и сборка обработчиков находятся в `app/mocks`;
- обработчики конкретной сущности могут находиться в её `api`-сегменте и экспортироваться через отдельную точку входа для mocks;
- обработчики уникального сценария теста задаются рядом с тестом;
- моковые ответы соответствуют API-контракту;
- RTK Query и UI не переключаются на отдельную реализацию запросов;
- включение в разработке задаётся явной настройкой, в production подмена отключена;
- не реализуем в обработчиках полноценный второй backend; необходимые изменения состояния имитируем минимально.

MSW не проверяет реальную реализацию backend. После подключения API отдельно проверяем совместную работу с сервером.

## 10. Проверка реализации

Используем Vitest; для компонентов предлагаем React Testing Library и DOM-окружение. MSW воспроизводит ответы согласованного API. Браузерные E2E-тесты не пишем. Предметные сценарии и серверные инварианты перечислены в [проверках backend](../backend/README.md#20-проверки-и-порядок-реализации); здесь проверяем клиентское поведение.

### Интерфейс питания

- Поля и динамические строки редактора, дробный ввод, ошибки, состояния сохранения и восстановление формы после сетевого сбоя.
- Различимые режимы создания, копирования и редактирования; передача revision и отображение конфликта.
- Поиск с загрузкой частями, пустые ответы, серверный отказ недоступного действия.
- Подтверждение отдельного блюда, отсутствие начисления на клиенте после времени плана, отображение итогов из API.
- Ручное сохранение съеденного за один шаг без дополнительного подтверждения.
- Раздельное отображение plannedNutrition/consumedNutrition; корректировка и отмена подтверждения с объяснением последствий.
- Корректные запросы после мутации текущего экрана; использование кеша до N и повторный запрос после N при следующем обращении. Свежесть проверяем управляемым временем.
- Очистка персонального кеша и отсутствие данных предыдущего пользователя.
- Адаптация недельной сетки в список дня на телефоне, клавиатурное управление, фокус и ошибки полей.

### Отдельные проверки авторизации

Проверяем экранные переходы, ошибки/таймеры кода, начальную загрузку, один refresh при параллельных запросах, координацию вкладок, очистку данных и сетевую ошибку выхода. Серверные требования и ограничения берём из [авторизации backend](../backend/README.md#17-авторизация-и-доступ).

Ручную приёмку выполняем на реальном backend после подключения сценария. Не пишем тесты внутренней структуры компонентов и стандартного поведения MUI; не реализуем бизнес-логику сервера внутри MSW.

## 11. Порядок реализации

Каждый сценарий проходит [общий цикл разработки](../README.md#порядок-разработки). Зависимости и приёмка функциональности определяются [этапами backend](../backend/README.md#этапы-реализации).

1. Инициализировать React + TypeScript + Vite, нужные слои FSD, тему MUI, роутер и API-слой.
2. Подключить формы, проверки, Vitest/MSW и простой кеш с настройкой N.
3. Реализовать и отдельно принять клиентский блок авторизации на согласованных ручках.
4. Подключать экраны продуктов, рецептов, расписания, подтверждения съеденного, дневника и целей по мере готовности API.
5. Проверять каждый подключённый сценарий на сервере, тестировать UI и выполнять ручную приёмку, включая телефон.
6. Будущие экраны добавлять на соответствующих этапах из [скоупа backend](../backend/README.md#1-задачи-и-этапы).
