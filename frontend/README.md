# Frontend трекера питания

Создан: 1 ноября 2026 года. Обновлён: 7 ноября 2026 года.

Документ описывает рабочий стек и архитектуру первой версии frontend. Приложение пока не инициализировано: это техническая основа для последующей реализации.

## 1. Назначение и границы первой версии

Адаптивное веб-приложение для создания блюд, планирования питания и ведения дневника. Основные сценарии должны быть удобны и на компьютере, и на телефоне.

Первая версия:

- регистрация по email/паролю, подтверждение почты кодом до входа в личный кабинет, вход и восстановление пароля по коду;
- поиск доступных продуктов и просмотр их КБЖУ;
- создание продукта пользователем или администратором одной формой с разной меткой происхождения;
- личные продукты при создании и последующая публикация автором для всех;
- быстрое добавление продукта в граммах через блюдо из одного ингредиента;
- каталог и карточки рецептов;
- создание неизменяемого блюда со списком ингредиентов; изменения сохраняются новым блюдом через «Создать на основе»;
- добавление выбранного блюда в личное расписание на определённую дату и время;
- изменение количества порций, перенос, копирование и удаление записей плана;
- плановое КБЖУ за день;
- три отметки съеденного: автоматический учёт, подтверждение пользователем, ручной ввод/корректировка;
- перенос и пропуск с сохранением явно записанного факта независимо от плана;
- незапланированная еда и история питания;
- цели КБЖУ с возможностью исправлять значения и даты в прошлом.

В MVP у всех аккаунтов только роль `USER`; семью, её создание и семейные роли не реализуем. Будущий семейный экран объединяет личные планы участников без создания копий. Упоминания административного кабинета и метки администратора ниже относятся к будущему этапу; в MVP создаётся только пользовательский контент без административных прав.

Следующие этапы: семейное редактирование, шаблоны недель, кладовая, список покупок, магазины, распознавание фотографий и прогнозирование закупок. Их интерфейсы и интеграции в первую версию не входят.

## 2. Стек технологий

### Рабочая основа

| Задача | Технология | Назначение |
|---|---|---|
| Интерфейс | React | Компоненты и взаимодействие с пользователем |
| Язык | TypeScript в strict-режиме | Типизация данных, компонентов и API-контрактов |
| Сборка | Vite | Локальная разработка и сборка SPA |
| Маршрутизация | React Router | Страницы, параметры маршрутов и URL-фильтры |
| Общее клиентское состояние | Redux Toolkit + React Redux | Настройки и состояние общих клиентских сценариев |
| Серверные данные | RTK Query | Запросы, мутации, кеширование и инвалидация |
| UI | Material UI (`@mui/material`) | Поля, кнопки, карточки, диалоги, навигация и layout |
| Стили компонентов | MUI theme, `sx`, `styled` | Единое оформление и локальная кастомизация |

| Проверка форм | Zod | Схемы и проверка значений формы |
| Тестирование | Vitest | Модульные и компонентные тесты |
| Подмена API в development | MSW | Моковые ответы backend для разработки интерфейса |
| Архитектура | Feature-Sliced Design (FSD) | Слои, слайсы, сегменты и явные границы зависимостей |

React + Redux — исходное пожелание пользователя. MUI, React Hook Form, Zod, Vitest, MSW и FSD явно выбраны пользователем. Остальные пункты — рабочая основа из обсуждения.

### Backend и границы frontend

Backend явно выбран пользователем:

| Задача | Технология | Назначение |
|---|---|---|
| Язык backend | Python | Серверная бизнес-логика и расчёты |
| API-фреймворк | FastAPI | REST API, проверка запросов и формирование OpenAPI |
| База данных | PostgreSQL | Постоянное хранение пользователей, рецептов, планов и дневника |

Frontend обращается к FastAPI по HTTP и обменивается JSON. Доступ к PostgreSQL, проверка прав, транзакции и окончательные расчёты выполняются на backend.

ORM, миграции и внутреннее устройство Python-приложения определяются в документации backend. Для авторизации согласованы email/пароль, коды подтверждения почты и JWT access/refresh; серверный контракт описан в разделе 17 документации backend, поведение веб-клиента — в разделе 8 этого документа.

## 3. Архитектура Feature-Sliced Design

Клиентское SPA с отдельным REST API на Python + FastAPI и базой PostgreSQL. Сервер отвечает за доступ к данным, сохранение, окончательные бизнес-проверки и достоверные расчёты. Frontend отвечает за отображение, ввод и предварительные расчёты для обратной связи.

Используем FSD: код разделяется на слои, внутри предметных слоёв — на слайсы, внутри слайсов — на технические сегменты (`ui`, `model`, `api`, `lib`, `config` по необходимости). Исходная схема была приближена к FSD; здесь явно разделяем бизнес-сущности, пользовательские действия и самостоятельные блоки интерфейса.

Порядок слоёв сверху вниз: `app → pages → widgets → features → entities → shared`. Создаём только нужные слои и слайсы, без пустых заготовок.

```text
frontend/
  src/
    app/
      providers/             # MUI, Redux и остальные провайдеры
      router/                # Маршруты и layout приложения
      store/                 # Настройка Redux store
      theme/                 # Тема MUI и настройки компонентов
      mocks/                 # Запуск MSW и сборка обработчиков

    pages/
      recipes/
      recipe-editor/
      products/              # Личные и публичные продукты
      meal-plan/
      diary/
      settings/

    widgets/                 # Крупные самостоятельные блоки, когда нужны
      meal-plan-calendar/
      daily-nutrition-summary/

    features/                # Пользовательские действия
      create-recipe/
        model/               # Схема Zod и логика формы
        ui/                  # Форма React Hook Form
        index.ts             # Публичный API слайса
      create-product/        # Общий сценарий пользователя и администратора
      publish-product/
      quick-add-product/
      confirm-consumption/
      add-meal-entry/
      move-meal-entry/
      adjust-consumption/
      skip-meal/
      edit-nutrition-goal/

    entities/                # Бизнес-сущности
      recipe/
        api/                 # Запросы и преобразования данных рецепта
        model/               # Модель и вычисления сущности
        ui/                  # RecipeCard и другие представления
        index.ts             # Публичный API слайса
      ingredient/
      meal-plan/
      meal-entry/
      nutrition-goal/

    shared/
      api/                   # Базовый RTK Query API и типы ошибок
        generated/           # Сгенерированные API-контракты, когда появится OpenAPI
      ui/                    # Общие элементы без привязки к одной области
      lib/                   # Форматирование, работа с датами и числами

    main.tsx
```

Это целевая схема. Каждый слайс в `pages`, `widgets`, `features`, `entities` при необходимости содержит свои сегменты и публичный API. `app` и `shared` делятся непосредственно на сегменты, без предметных слайсов.

### Правила зависимостей

- Слайс может импортировать другие слайсы только с нижележащих слоёв.
- Слайсы одного слоя не импортируют друг друга. Их взаимодействие собираем выше: в feature, widget или page в зависимости от задачи.
- Внешние потребители используют публичный API слайса (`index.ts`), без импорта его внутренних файлов.
- Внутри слайса используем прямые относительные импорты, чтобы не создавать циклы через собственный публичный API.
- `app` связывает приложение, провайдеры и маршрутизацию.
- `pages` собирают экраны. Уникальный блок страницы можно оставить внутри неё.
- `widgets` объединяют сущности и действия в самостоятельные блоки интерфейса.
- `features` описывают действия: создать блюдо на основе существующего, создать/опубликовать продукт, подтвердить еду, добавить или перенести блюдо, скорректировать съеденное, пропустить приём.
- `entities` содержат модели, API и представления бизнес-сущностей.
- `shared` содержит общую инфраструктуру и UI без бизнес-логики питания; он не импортирует верхние слои.
- Предметная специфичность определяет место кода. Не переносим его в `shared` только ради обхода правил импорта.

Пример: `entities/recipe` предоставляет карточку и данные рецепта, `features/create-recipe` — создание нового блюда, в том числе на основе существующего, `pages/recipe-editor` собирает экран. Кнопки действий можно передавать в карточку через props: сущность не импортирует feature.

Базовый RTK Query API находится в `shared/api`. Запросы сущностей подключаются в `entities/*/api`; запросы, относящиеся к конкретному пользовательскому действию, могут находиться в `features/*/api`. Один endpoint не дублируем в нескольких слайсах.

## 4. Где хранится состояние

| Данные | Место хранения |
|---|---|
| Рецепты, продукты, план, дневник и серверные итоги | Кеш RTK Query |
| Черновик нового блюда, в том числе созданного на основе существующего | Состояние формы |
| Открытый диалог, локальное раскрытие карточки | Локальное состояние React |
| Выбранная неделя или дата, поисковая строка, фильтры | URL, если состояние полезно сохранять при переходе или обновлении страницы |
| Общие клиентские настройки, нужные разным экранам | Redux slices при необходимости |
| Предварительное КБЖУ черновика | Вычисление из полей формы |

Не копируем ответы RTK Query в отдельные Redux slices. Не храним вычисляемые итоги как независимое изменяемое состояние. Не сохраняем весь Redux store в `localStorage`.

Настройки отображения можно сохранять отдельно. Сохранение черновиков между перезагрузками — дополнительный сценарий, который требует отдельного решения.

## 5. MUI и оформление

Основной UI-набор — MUI. Вторую библиотеку готовых компонентов в первой версии не добавляем без конкретной необходимости.

- В `app/theme` определяем палитру, типографику, отступы, скругления и общие настройки компонентов.
- Повторяющиеся настройки полей, кнопок и карточек задаём через тему и `components` overrides.
- `sx` используем для локальных изменений и компоновки.
- `styled` используем для повторяемых оформленных компонентов, когда это упрощает код.
- Общую тему создаём централизованно, без независимых палитр внутри функциональных модулей.
- Не оборачиваем каждый компонент MUI автоматически. Обёртка нужна, когда она добавляет поведение или закрепляет соглашение проекта.
- Учитываем клавиатурное управление, видимый фокус, подписи полей, ошибки и контраст.

MUI даёт основу Material Design; внешний вид приложения уточняется собственной темой.

Для первой версии достаточно стандартных компонентов MUI. MUI X рассматриваем отдельно, если появится конкретная потребность в таблицах, графиках или выборе дат. Часть возможностей MUI X имеет коммерческую лицензию; обычное расписание питания не требует покупки этих компонентов.

## 6. Основные экраны и компоненты

### Продукты: создание, публикация и происхождение

В поиске доступны собственные личные Ingredient, публичные продукты других авторов и доступные StoreProduct при наличии данных магазина. Ingredient — карточка человека, StoreProduct — отдельная конкретная позиция магазина. Публикация Ingredient не превращает её в магазинный товар.

Форма создания продукта общая для пользователя и администратора: название, состояние, КБЖУ на 100 г, необязательные бренд/штрихкод и сведения об источнике. Метку «создан пользователем» / «создан администратором» определяет сервер по типу кабинета; в форме нет самостоятельного переключателя этой метки.

Новый продукт виден только автору. Позже автор может открыть его всем пользователям действием публикации; ID, автор и происхождение сохраняются. Обязательной модерации публикации в MVP нет. Обратное скрытие убирает продукт из нового общего поиска, сохраняя состав уже созданных блюд и историю. Видимость и происхождение показываются раздельно.

Автор может исправлять свою карточку. Исправление КБЖУ не меняет ранее сохранённые блюда; при создании нового блюда используются пищевые данные выбранного продукта. Полные каталоги магазинов, сравнение цен и автоматическое сопоставление — следующие этапы. Пользовательский продукт можно использовать без связи с магазином.

### Каталог блюд

Поиск, загрузка результатов частями, карточки и переход к созданию блюда. Весь каталог продуктов или блюд целиком не загружается.

`RecipeCard` показывает название, изображение при наличии, выход и КБЖУ на порцию. Действия: открыть, «Создать на основе», добавить в план и архивировать собственное блюдо. Переключателя версий нет.

Сохранённая запись ссылается на выбранное неизменяемое блюдо. Создание изменённой копии не заменяет блюдо в планах, дневниках или у других пользователей. Архивирование убирает карточку из обычного выбора, не нарушая историю. Простые блюда из одного продукта отделены фильтром от обычных рецептов.

### Создание блюда

Поля: название, выход порций, состав с количеством в граммах, необязательная инструкция и готовый вес. Источником строки может быть доступный продукт пользователя/администратора или конкретный магазинный товар. У строки всегда один источник; форма показывает его происхождение.

Список состава реализуем через useFieldArray из React Hook Form, проверку — Zod и zodResolver. Поиск имеет небольшую задержку и загрузку частями. Количество во время ввода может быть строкой; десятичный разделитель нормализуем, пустое поле не превращаем в ноль.

Frontend показывает предварительное КБЖУ. Backend фиксирует снимки пищевых значений и возвращает итог. «Создать на основе» заполняет черновик из доступного блюда, а сохранение создаёт новый ID. Интерфейс явно сообщает, что существующее блюдо и ранее добавленные записи сохраняются. Черновик можно менять до сохранения; сохранённое содержание не редактируется на месте.

### Быстрое добавление продукта — MVP

Сценарий: выбрать продукт → ввести граммы и фактическое время → сохранить. Пользователь не заполняет редактор рецепта, название или выход. Под капотом используется неизменяемое блюдо single_product с одним ингредиентом на 100 г и готовым весом 100 г; интерфейс показывает привычные граммы.

В дневнике это manual с отметкой «Введено или скорректировано пользователем». То же простое блюдо можно запланировать на будущее. Если продукт отсутствует, доступно создание личной карточки и последующее добавление. Её публикация не обязательна для собственного использования. Повторное использование простого блюда учитывает снимок КБЖУ: после исправления продукта старый снимок не выдаётся за новый.

### План питания

На компьютере — недельная сетка, на телефоне — выбранный день и вертикальный список. В одном приёме может быть несколько блюд. MealPlan — личный недельный контейнер scheduled; manual не требует недели.

Карточка разделяет план и съеденное: плановые блюдо, время и порции, пропуск, фактические время/блюдо/количество и способ учёта при наличии. В семейном режиме позже добавляется владелец. Общие части карточки используются в расписании и дневнике.

Перенос выполняется действием «Перенести»; drag-and-drop отложен. Если есть явный факт, интерфейс объясняет, что перенос меняет расписание, а съеденное остаётся на фактической дате. То же правило действует при изменении плановых порций/блюда и пропуске.

### Дневник и три отметки

| Отметка | Значение |
|---|---|
| Учтено автоматически | Наступило время непропущенного плана, пользователь не сохранял явный факт |
| Подтверждено пользователем | Пользователь подтвердил время и количество съеденного |
| Введено или скорректировано пользователем | Ручное питание либо исправление фактических данных |

У исправленного и затем подтверждённого питания основная отметка остаётся о ручном вводе/корректировке, а подтверждение показывается дополнительно. Изменение только плана не считается подтверждением еды. Автоматическое предположение визуально различается с явным действием.

Действия: подтвердить, указать «Уже съел», исправить фактические время/количество, добавить manual, перенести или пропустить план. Подтверждение фиксирует фактические количество и блюдо отдельно от плана; после этого они не следуют за его изменениями. Фактическое время нельзя задавать в будущем. Можно подтвердить еду до планового времени.

Дневник и расписание используют одну MealEntry. Явный факт учитывается ровно один раз и имеет приоритет над автоматикой. До появления факта scheduled учитывается после планового времени, если запись не удалена и не пропущена.

Порции и готовые граммы допустимы для факта. Если готовый вес блюда неизвестен, показываем объяснение и предлагаем порции. Для single_product готовый вес известен автоматически. Плановые и учтённые КБЖУ отображаются отдельно.

Пример без подтверждения: в 14:00 обед на 13:00 учтён автоматически; перенос на 18:00 убирает его вклад до 18:00. Пример с подтверждением: обед явно записан на 12:30; перенос плана на 18:00 сохраняет съеденное на 12:30. Если меняются даты, обновляются все затронутые плановые и фактические дни.

Пропуск плана не стирает явный факт. Полное удаление записи исключает оба; это отдельное действие. Снятие только подтверждения сохраняет корректировки; если было только подтверждение без ручных изменений, его отмена полностью сбрасывает явный факт. При полном сбросе факта scheduled объясняем возврат автоматических правил; manual можно исправить или удалить, автоматического режима у неё нет.

Данные обновляются при ближайшей автоматической границе времени, возврате на экран и восстановлении соединения. Для явно записанного факта наступление времени плана не создаёт дополнительного питания. Постоянное WebSocket-соединение для этого сценария не требуется.

### Цели КБЖУ

В настройках показываем периоды целей. Можно исправить значения/даты прошлого периода, удалить ошибочный период и изменить общую границу соседних. Показываем затронутые даты; сервер проверяет отсутствие пересечений. Изменение цели обновляет сравнение с нормой, сохраняя количества и КБЖУ еды.

## 7. Предметные правила, важные для frontend

- **Блюдо (Recipe)** неизменяемо после сохранения. Изменение создаёт новое самостоятельное блюдо с новым ID; версий и их переключения нет. Новая копия не заменяет исходник у других людей или в существующих записях.
- **RecipeItem** хранит снимок состава и КБЖУ. Исправление исходного продукта, смена его видимости или архивирование не пересчитывает старые блюда и съеденное.
- **Ingredient и StoreProduct** — разные сущности. Первый создаётся пользователем либо администратором одной формой с серверной меткой происхождения; второй представляет реальную позицию магазина. Связь между ними не устанавливается только по названию.
- **Видимость продукта** независима от метки автора. Созданный продукт личный; автор может открыть его всем. Публикация сохраняет ID и не присваивает пользовательской карточке административное происхождение.
- **Быстрый ввод** использует single_product: блюдо с одной строкой на 100 г, одной технической порцией и готовым весом 100 г. Пользователь вводит граммы без редактора рецепта.
- **MealPlan** принадлежит пользователю и объединяет scheduled недели; manual не требует контейнера.
- **MealEntry** сохраняет происхождение scheduled/manual независимо от способа учёта. Подтверждение не превращает scheduled в manual.
- **Способ учёта** — автоматический, подтверждение либо ручной ввод/корректировка. Подтверждение и корректировка могут сохраняться одновременно; повторного вклада нет.
- **Явный факт** имеет собственные время, пояс, блюдо и количество. Он может быть записан до времени плана и остаётся на своей дате при переносе плана, смене плановых порций/блюда и пропуске.
- **Автоматический вклад** зависит от времени/пропуска только при отсутствии явного факта. Наступление времени не создаёт строку. Сброс явного факта scheduled возвращает эти правила, что объясняется пользователю.
- Количество — порции или граммы готового блюда при известном готовом весе. Ингредиенты MVP задаются в граммах; штуки, ложки и миллилитры с коэффициентами перевода отложены.
- Модель приготовления остаётся упрощённой, без потерь/коэффициентов. Базовые моменты и часовой пояс сохраняются; расширенные сценарии смены поясов отложены.
- Копирование создаёт независимые scheduled с тем же выбранным блюдом и новыми датами; фактические данные, подтверждение, корректировки и пропуск не копируются.
- Время приёма по умолчанию превращается в конкретное время записи; изменение настройки не переносит существующие позиции.
- У пользователя может не быть семьи, активная семья — не более одной. Личные данные сохраняются при вступлении и выходе. Личная семья из одного человека не создаётся.
- Будущий семейный экран объединяет доступные личные записи без копирования. Дневник семьи учитывает все периоды участия, включая бывших участников, исключая перерывы. Возвращение создаёт новый период; эти возможности не входят в MVP.
- Для семейной истории автоматическое питание относится к scheduled_at, явный факт — к consumed_at. Перенос плана с явным фактом не меняет его период членства; видимость истории задаётся отдельно.
- Цели редактируются и в прошлом; пересчитывается сравнение с нормой, а не съеденное.
- Закупки позже используют снимок списка и плановые порции. Обновление после изменения источников выполняется явно с сохранением купленного. Предпочтения бренда и допустимые замены не угадываются по общему названию.

Эти правила требуют поддержки API. Окончательные DTO определяются backend-контрактом, а не локальными предположениями компонентов.

## 8. Взаимодействие с API

```text
React + MUI → RTK Query → REST API (FastAPI / Python) → PostgreSQL
```

Бизнес-endpoint планируем под префиксом `/api/v1`. Адрес API задаём централизованно через конфигурацию, без адресов сервера в компонентах. Для локальной разработки согласуем Vite proxy или CORS на FastAPI в зависимости от способа подключения.

Один базовый `createApi` для backend. Endpoint отдельных областей подключаются через `injectEndpoints`. Для стандартных JSON-запросов используем `fetchBaseQuery`.

Поток изменения данных:

```text
Действие пользователя
  → RTK Query mutation
  → проверка и сохранение на backend
  → успешный ответ
  → инвалидация соответствующих тегов
  → повторная загрузка активных запросов
  → обновлённые данные и итоги на экране
```

Теги планируем по областям: рецепты, план, дневник. Ключи кеша должны учитывать значимые параметры: семью, период и пользователя, когда они участвуют в запросе. При завершении сессии очищаем кеш персональных данных.

Создание обоих типов, чтение и редактирование выполняются через `/api/v1/meal-entries`. Создание задаёт kind; PATCH сохраняет правила выбранного типа. Дневник и расписание являются представлениями тех же entryId. Для мутаций используем теги MealEntry и затронутых экранов; manual обновляет дневник, а scheduled — также свой MealPlan и семейное расписание при наличии доступа.

После сохранения рецепта обновляем его карточку, списки и выбор версий. Закреплённые версии в существующих планах и дневнике сохраняются; массового обновления недель нет.

Перенос, пропуск, смена плановых порций, корректировка количества и явная замена версии обновляют соответствующие планы, дневник и dashboard. Изменение цели обновляет сравнение за затронутые даты. После смены семьи загружаем её контекст, а собственные планы остаются теми же объектами.

У автоматического дневника итоги меняются и без мутации — с течением времени. Учитываем `nextStatusChangeAt`, не держим устаревший итог только потому, что никто не изменял базу. Эту границу и возврат в приложение обрабатываем через повторный запрос.

RTK Query не нормализует автоматически одну сущность между всеми ответами API. Связанные экраны обновляем явной инвалидацией или контролируемым обновлением кеша.

В первой реализации после мутации получаем серверный результат без сложной оптимистической синхронизации. Позже оптимистические изменения добавляются для конкретных действий с откатом при ошибке.

Обрабатываем загрузку, пустой результат, ошибку валидации, потерю авторизации, сетевую ошибку и конфликт версии. При конфликте изменения плана не перезаписываем чужую работу автоматически.

### Регистрация и JWT access/refresh

- Регистрация: email/пароль → экран ввода кода из почты → подтверждение → личный кабинет. До подтверждения токены не выдаются и персональные запросы не выполняются. Для шага кода используется `challengeId` из ответа backend.
- Обычный вход после подтверждения — email/пароль, без почтового кода. Ответ `email_verification_required` после правильного пароля переводит на подтверждение почты.
- Восстановление: email → ввод нового кода и нового пароля → успешный сброс → экран обычного входа. Код восстановления отличается по назначению от кода регистрации. После сброса backend отзывает все прежние сеансы.
- Экран кода показывает срок действия, ошибки и таймер повторной отправки по данным backend. Переотправка делает старый код недействительным. Ответ запроса восстановления одинаков для существующего и неизвестного email.
- Единственная роль — `USER`. Семейных экранов и переключения ролей в MVP нет. Защита маршрутов улучшает UX; доступ к каждому объекту проверяет backend.
- Access JWT хранится только в памяти приложения и добавляется в `Authorization: Bearer`. Его не сохраняем в `localStorage`, `sessionStorage` или persisted Redux. Пароли и почтовые коды не сохраняются между запусками.
- Refresh JWT браузер получает в `HttpOnly; Secure; SameSite=Lax` cookie для `/api/v1/auth`; JavaScript не читает его. Для auth-cookie запросов включаем credentials и передаём CSRF-токен, полученный через GET `/api/v1/auth/csrf`; backend также проверяет Origin. Предпочтительно использовать один origin для приложения и `/api`.
- После перезагрузки запрашиваем новый access через `/auth/refresh`, затем `/users/me` (с префиксом `/api/v1`). До завершения начальной проверки показываем загрузку, не выполняем персональные запросы и не перенаправляем преждевременно на вход.
- Общая обёртка RTK Query при `401` бизнес-запроса выполняет один refresh и повторяет исходный запрос не более одного раза. Параллельные запросы ожидают общий результат обновления; auth-маршруты не запускают рекурсивный refresh. `403` не запускает обновление токена.
- Backend ротирует refresh при каждом использовании. Обновление сериализуется также между вкладками одного origin, чтобы одновременная ротация не привела к повторному использованию уже погашенного refresh; механизм координации выбираем при реализации.
- При окончательном отказе refresh или выходе очищаем access, текущего пользователя и кеш персональных данных RTK Query. Выход вызывает `/auth/logout` для отзыва сеанса и удаления cookie; при сетевой ошибке локальные данные очищаются, но интерфейс не заявляет об успешном серверном отзыве.

Стартовые серверные настройки, изменяемые конфигурацией: access на 15 минут, refresh-сеанс на 30 дней без продления абсолютного срока ротацией; код на 10 минут, 5 попыток и повторная отправка не чаще раза в 60 секунд. Клиент использует сроки и ограничения из API. DTO и ответы ошибок задаются OpenAPI, а не дублируются независимыми клиентскими правилами.

Для защиты от повторных нажатий показываем состояние сохранения. Операции, где повтор создаёт дубликат, требуют согласованной с backend идемпотентности.

## 9. API-контракты и проверки

FastAPI формирует OpenAPI на основе описания маршрутов и схем Pydantic. Эту спецификацию используем как источник API-контрактов для frontend. Планируем получать её через `/openapi.json` и генерировать TypeScript-контракты и, при удобстве, RTK Query endpoint через `@rtk-query/codegen-openapi`.

Для каждой ручки действует порядок [«прото → backend → frontend»](../README.md#порядок-разработки). Frontend подключает ручку после согласования её контракта, реализации и проверки backend. Все API заранее проектировать не требуется; детали очередного сценария уточняем перед его реализацией. Изменение контракта сначала согласовываем, затем реализуем на backend и переносим во frontend.

```text
Согласованные маршруты и схемы Pydantic/OpenAPI (прото)
  → реализация и проверка ручки backend
  → TypeScript-контракты / RTK Query endpoint
  → frontend на готовой ручке
```

- Сгенерированный код не редактируем вручную.
- Теги кеша и дополнительное поведение задаём в расширении API.
- ORM-модели backend не импортируем в frontend.
- API DTO и значения формы могут различаться: преобразование выполняется явно.
- TypeScript проверяет код при разработке, но не проверяет произвольные данные во время выполнения.
- Проверка формы улучшает UX; backend независимо проверяет данные и права доступа.

Zod проверяет ввод пользователя на клиенте, Pydantic — данные запросов на сервере. Python-модели нельзя напрямую импортировать в TypeScript. Клиентские формы согласуем с OpenAPI; генерация TypeScript-типов сама по себе не создаёт Zod-схемы и не заменяет проверку значений во время выполнения.

Формат ошибок API и преобразование серверных ошибок полей в ошибки React Hook Form согласуем с backend и реализуем в API-адаптерах слайсов. Чистые TypeScript-расчёты на клиенте дают предварительный результат; окончательные значения возвращает Python-backend.

### Будущий мобильный клиент

Тот же REST API должен обслуживать веб-приложение и будущий мобильный клиент. Язык backend не ограничивает выбор мобильной технологии. Используем JWT access/refresh; хранение refresh в защищённом хранилище ОС и его передачу согласуем на мобильном этапе. Правила браузерной HttpOnly-cookie относятся к веб-клиенту.

React Native + Expo обсуждался как вариант для мобильного приложения, но пока не выбран окончательно. При таком выборе можно переиспользовать API-контракты, Zod-схемы и чистые TypeScript-функции, если они не зависят от браузера. UI на MUI остаётся веб-интерфейсом; мобильные компоненты создаются отдельно.

### Подмена API через MSW в development

MSW (Mock Service Worker) — выбранный инструмент для подмены API в development. Он перехватывает HTTP-запросы и возвращает заранее описанные моковые ответы backend. В браузере используется Service Worker. Отдельный backend-процесс для таких ответов запускать не требуется.

Обработчики имитируют ответы FastAPI. При отключении подмены те же запросы RTK Query уходят на реальный backend.

```text
Без подмены: компонент → RTK Query → backend → ответ
С MSW:      компонент → RTK Query → обработчик MSW → тестовый ответ
```

Основная разработка экранов идёт на готовых ручках backend. MSW используем по уже согласованному контракту, чтобы воспроизводить пустые ответы, задержки, ошибки доступа и ошибки сервера. При необходимости те же обработчики можно использовать в тестах Vitest.

Правила использования:

- запуск и сборка обработчиков находятся в `app/mocks`;
- обработчики конкретной сущности могут находиться в её `api`-сегменте и экспортироваться через отдельную точку входа для mocks;
- обработчики уникального сценария теста задаются рядом с тестом;
- моковые ответы соответствуют API-контракту;
- RTK Query и UI не переключаются на отдельную реализацию запросов;
- включение в разработке задаётся явной настройкой, в production подмена отключена;
- не реализуем в обработчиках полноценный второй backend; необходимые изменения состояния имитируем минимально.

MSW не проверяет реальную реализацию backend. После подключения API отдельно проверяем совместную работу с сервером.

## 10. Проверка реализации

Тесты запускаем через Vitest. Для компонентных тестов предлагаем React Testing Library и DOM-окружение. Сквозные тесты не пишем.

Приоритет — сценарии с риском ошибочных данных:

- регистрация без доступа до кода, неверный/истёкший код, повторная отправка и обычный вход без кода после подтверждения;
- восстановление пароля по отдельному коду и возврат на вход;
- начальное восстановление access, единичный refresh при параллельных `401`, отказ обновления и очистка персонального кеша;
- координация refresh между вкладками, выход и обработка сетевой ошибки при отзыве сеанса;
- масштабирование КБЖУ по количеству порций;
- добавление и удаление ингредиентов в редакторе;
- корректный ввод дробных количеств;
- обновление плана и итогов после мутации;
- различие планового и фактического количества;
- создание нового блюда при изменении без перезаписи оригинала;
- неизменность старых блюд, расписания и съеденного после исправления КБЖУ продуктов;
- одна форма создания продукта и правильная метка пользователя/администратора;
- личная видимость при создании, публикация для всех и сохранение ID/происхождения;
- скрытие продукта из поиска без разрушения ранее сохранённой истории;
- быстрое добавление продукта в граммах без заполнения редактора рецепта;
- автоматический учёт по серверному времени и исчезновение только автоматического вклада после переноса в будущее;
- три отметки питания и сохранение подтверждения вместе с корректировкой;
- подтверждение до планового времени;
- сохранение явного факта при переносе в другую неделю, смене плановых порций/блюда и пропуске;
- явный сброс факта и возврат автоматического правила без двойного учёта;
- ввод съеденного в граммах при известном готовом весе, пропуск и незапланированная еда;
- создание и редактирование MealEntry обоих типов, разные обязательные поля формы и отсутствие дублирования записи между календарём и дневником;
- редактирование прошлых целей и границ без изменения съеденных количеств;
- сохранение личного расписания при выходе из семьи;
- ошибки сети, повторное сохранение и конфликт редактирования.

Основные сценарии приёмки: автоматический обед на 13:00 в 14:00 перенести на 18:00 и увидеть исчезновение/возврат вклада; подтверждённый на 12:30 обед перенести на 18:00 и увидеть сохранение факта на 12:30. Проверяем быстрое добавление продукта, публикацию личной карточки, создание изменённого блюда новым ID и исправление прошлой цели. В Vitest/MSW используем управляемое время, без реального ожидания часов.

Не нужны тесты, которые только повторяют внутреннюю структуру компонентов или проверяют стандартное поведение MUI.

## 11. Порядок реализации

Каждую ручку в перечисленных сценариях подключаем после её согласованного прото, реализации и проверки backend. Цикл повторяется по мере разработки; готовность всего backend для начала frontend не требуется. MSW дополняет тестирование отдельных состояний.

1. Инициализировать React + TypeScript + Vite и базовую структуру FSD.
2. Подключить MUI, тему, маршрутизацию, Redux с RTK Query, React Hook Form, Zod, Vitest и MSW для development. Реализовать регистрацию/подтверждение почты, вход, JWT access/refresh, выход и восстановление пароля; единственная роль — `USER`.
3. Реализовать поиск и создание продуктов пользователем, личную видимость и публикацию; каталог и создание неизменяемых блюд.
4. Реализовать личное расписание, выбор блюда, время, порции и перенос.
5. Реализовать дневник с тремя отметками учёта, независимым явным фактом, корректировками, пропусками, быстрым добавлением продукта и историей целей.
6. Выполнить ручную приёмку основного сценария, проверить адаптацию под телефон и тесты Vitest.
7. Развивать семейный режим, административный кабинет, покупки и ИИ отдельными этапами.
