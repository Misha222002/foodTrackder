# Frontend трекера питания

Создан: 1 ноября 2026 года. Обновлён: 3 ноября 2026 года.

Документ описывает рабочий стек и архитектуру первой версии frontend. Приложение пока не инициализировано: это техническая основа для последующей реализации.

## 1. Назначение и границы первой версии

Адаптивное веб-приложение для создания блюд, планирования питания и ведения дневника. Основные сценарии должны быть удобны и на компьютере, и на телефоне.

Первая версия:

- поиск продуктов и просмотр их КБЖУ;
- каталог и карточки рецептов;
- создание и редактирование рецепта со списком ингредиентов;
- добавление рецепта в расписание на определённую дату и приём пищи;
- изменение количества порций, перенос, копирование и удаление записей плана;
- плановое КБЖУ за день;
- отметка фактически съеденного и просмотр истории питания.

Следующие этапы: семейное редактирование, шаблоны недель, кладовая, список покупок, магазины, распознавание фотографий и прогнозирование закупок. Их интерфейсы и интеграции в первую версию не входят.

## 2. Стек технологий

### Рабочая основа

| Задача | Технология | Назначение |
|---|---|---|
| Интерфейс | React | Компоненты и взаимодействие с пользователем |
| Язык | TypeScript в strict-режиме | Типизация данных, компонентов и API-контрактов |
| Сборка | Vite | Локальная разработка и сборка SPA |
| Маршрутизация | React Router | Страницы, параметры маршрутов и URL-фильтры |
| Общее клиентское состояние | Redux Toolkit + React Redux | Настройки и состояние общих клиентских сценариев |
| Серверные данные | RTK Query | Запросы, мутации, кеширование и инвалидация |
| UI | Material UI (`@mui/material`) | Поля, кнопки, карточки, диалоги, навигация и layout |
| Стили компонентов | MUI theme, `sx`, `styled` | Единое оформление и локальная кастомизация |

| Проверка форм | Zod | Схемы и проверка значений формы |
| Тестирование | Vitest | Модульные и компонентные тесты |
| Подмена API в development | MSW | Моковые ответы backend для разработки интерфейса |
| Архитектура | Feature-Sliced Design (FSD) | Слои, слайсы, сегменты и явные границы зависимостей |

React + Redux — исходное пожелание пользователя. MUI, React Hook Form, Zod, Vitest, MSW и FSD явно выбраны пользователем. Остальные пункты — рабочая основа из обсуждения.

### Backend и границы frontend

Backend явно выбран пользователем:

| Задача | Технология | Назначение |
|---|---|---|
| Язык backend | Python | Серверная бизнес-логика и расчёты |
| API-фреймворк | FastAPI | REST API, проверка запросов и формирование OpenAPI |
| База данных | PostgreSQL | Постоянное хранение пользователей, рецептов, планов и дневника |

Frontend обращается к FastAPI по HTTP и обменивается JSON. Доступ к PostgreSQL, проверка прав, транзакции и окончательные расчёты выполняются на backend.

ORM, миграции, серверная авторизация и внутреннее устройство Python-приложения определяются отдельно в документации backend. В этом документе они не фиксируются.

### Дополнительные инструменты

| Задача | Инструмент | Статус |
|---|---|---|
| Работа с React-компонентами в тестах | React Testing Library | Предлагаемый вспомогательный инструмент для Vitest |

## 3. Архитектура Feature-Sliced Design

Клиентское SPA с отдельным REST API на Python + FastAPI и базой PostgreSQL. Сервер отвечает за доступ к данным, сохранение, окончательные бизнес-проверки и достоверные расчёты. Frontend отвечает за отображение, ввод и предварительные расчёты для обратной связи.

Используем FSD: код разделяется на слои, внутри предметных слоёв — на слайсы, внутри слайсов — на технические сегменты (`ui`, `model`, `api`, `lib`, `config` по необходимости). Исходная схема была приближена к FSD; здесь явно разделяем бизнес-сущности, пользовательские действия и самостоятельные блоки интерфейса.

Порядок слоёв сверху вниз: `app → pages → widgets → features → entities → shared`. Создаём только нужные слои и слайсы, без пустых заготовок.

```text
frontend/
  src/
    app/
      providers/             # MUI, Redux и остальные провайдеры
      router/                # Маршруты и layout приложения
      store/                 # Настройка Redux store
      theme/                 # Тема MUI и настройки компонентов
      mocks/                 # Запуск MSW и сборка обработчиков

    pages/
      recipes/
      recipe-editor/
      meal-plan/
      diary/
      settings/

    widgets/                 # Крупные самостоятельные блоки, когда нужны
      meal-plan-calendar/
      daily-nutrition-summary/

    features/                # Пользовательские действия
      edit-recipe/
        model/               # Схема Zod и логика формы
        ui/                  # Форма React Hook Form
        index.ts             # Публичный API слайса
      add-meal-to-plan/
      move-planned-meal/
      log-meal/

    entities/                # Бизнес-сущности
      recipe/
        api/                 # Запросы и преобразования данных рецепта
        model/               # Модель и вычисления сущности
        ui/                  # RecipeCard и другие представления
        index.ts             # Публичный API слайса
      ingredient/
      planned-meal/
      food-log-entry/

    shared/
      api/                   # Базовый RTK Query API и типы ошибок
        generated/           # Сгенерированные API-контракты, когда появится OpenAPI
      ui/                    # Общие элементы без привязки к одной области
      lib/                   # Форматирование, работа с датами и числами

    main.tsx
```

Это целевая схема. Каждый слайс в `pages`, `widgets`, `features`, `entities` при необходимости содержит свои сегменты и публичный API. `app` и `shared` делятся непосредственно на сегменты, без предметных слайсов.

### Правила зависимостей

- Слайс может импортировать другие слайсы только с нижележащих слоёв.
- Слайсы одного слоя не импортируют друг друга. Их взаимодействие собираем выше: в feature, widget или page в зависимости от задачи.
- Внешние потребители используют публичный API слайса (`index.ts`), без импорта его внутренних файлов.
- Внутри слайса используем прямые относительные импорты, чтобы не создавать циклы через собственный публичный API.
- `app` связывает приложение, провайдеры и маршрутизацию.
- `pages` собирают экраны. Уникальный блок страницы можно оставить внутри неё.
- `widgets` объединяют сущности и действия в самостоятельные блоки интерфейса.
- `features` описывают пользовательские действия: редактировать рецепт, добавить блюдо, отметить съеденное.
- `entities` содержат модели, API и представления бизнес-сущностей.
- `shared` содержит общую инфраструктуру и UI без бизнес-логики питания; он не импортирует верхние слои.
- Предметная специфичность определяет место кода. Не переносим его в `shared` только ради обхода правил импорта.

Пример: `entities/recipe` предоставляет карточку и данные рецепта, `features/edit-recipe` — его редактирование, `pages/recipe-editor` собирает экран. Кнопки действий можно передавать в карточку через props: сущность не импортирует feature.

Базовый RTK Query API находится в `shared/api`. Запросы сущностей подключаются в `entities/*/api`; запросы, относящиеся к конкретному пользовательскому действию, могут находиться в `features/*/api`. Один endpoint не дублируем в нескольких слайсах.

## 4. Где хранится состояние

| Данные | Место хранения |
|---|---|
| Рецепты, продукты, план, дневник и серверные итоги | Кеш RTK Query |
| Черновик создаваемого или редактируемого рецепта | Состояние формы |
| Открытый диалог, локальное раскрытие карточки | Локальное состояние React |
| Выбранная неделя или дата, поисковая строка, фильтры | URL, если состояние полезно сохранять при переходе или обновлении страницы |
| Общие клиентские настройки, нужные разным экранам | Redux slices при необходимости |
| Предварительное КБЖУ черновика | Вычисление из полей формы |

Не копируем ответы RTK Query в отдельные Redux slices. Не храним вычисляемые итоги как независимое изменяемое состояние. Не сохраняем весь Redux store в `localStorage`.

Настройки отображения можно сохранять отдельно. Сохранение черновиков между перезагрузками — дополнительный сценарий, который требует отдельного решения.

## 5. MUI и оформление

Основной UI-набор — MUI. Вторую библиотеку готовых компонентов в первой версии не добавляем без конкретной необходимости.

- В `app/theme` определяем палитру, типографику, отступы, скругления и общие настройки компонентов.
- Повторяющиеся настройки полей, кнопок и карточек задаём через тему и `components` overrides.
- `sx` используем для локальных изменений и компоновки.
- `styled` используем для повторяемых оформленных компонентов, когда это упрощает код.
- Общую тему создаём централизованно, без независимых палитр внутри функциональных модулей.
- Не оборачиваем каждый компонент MUI автоматически. Обёртка нужна, когда она добавляет поведение или закрепляет соглашение проекта.
- Учитываем клавиатурное управление, видимый фокус, подписи полей, ошибки и контраст.

MUI даёт основу Material Design; внешний вид приложения уточняется собственной темой.

Для первой версии достаточно стандартных компонентов MUI. MUI X рассматриваем отдельно, если появится конкретная потребность в таблицах, графиках или выборе дат. Часть возможностей MUI X имеет коммерческую лицензию; обычное расписание питания не требует покупки этих компонентов.

## 6. Основные экраны и компоненты

### Каталог рецептов

Поиск, загрузка результатов частями, карточки и переход в редактор. Поиск не должен загружать весь каталог продуктов или рецептов целиком.

`RecipeCard` показывает рецепт: название, изображение при наличии, выход порций и КБЖУ на порцию. Основные действия — открыть, редактировать и добавить в план.

### Редактор рецепта

Основные поля:

- название;
- выход рецепта в порциях;
- список ингредиентов с количеством в граммах;
- инструкция приготовления — необязательно;
- вес готового блюда — необязательно.

Динамический список ингредиентов реализуем через `useFieldArray` из React Hook Form. Проверку значений задаём схемой Zod и подключаем через `zodResolver` из `@hookform/resolvers`. Поиск ингредиентов выполняем с небольшой задержкой перед запросом и загрузкой результатов частями.

Количество в форме может временно быть строкой: пользователь ещё вводит значение. Перед запросом нормализуем десятичный разделитель и проверяем число. Пустое поле не превращаем незаметно в ноль.

Frontend показывает предварительное КБЖУ, backend повторяет проверки и возвращает итог. Отправленные клиентом суммы не считаются достоверными.

### План питания

На компьютере — недельная сетка. На телефоне — выбранный день и вертикальный список приёмов пищи. В одном приёме пищи может быть несколько блюд.

`PlannedMealCard` показывает конкретную запись: дату, тип приёма пищи, количество порций, участников при их наличии и КБЖУ. Карточка рецепта и карточка записи плана — отдельные компоненты с общими визуальными частями.

В первой версии перенос выполняется через действие «Перенести». Drag-and-drop добавляется отдельно после готовности основного сценария.

### Дневник

Показывает фактически съеденное за выбранный день. Позволяет отметить блюдо из плана как съеденное, изменить реальное количество, отметить пропуск и добавить незапланированную еду. Запись дневника может существовать без записи плана.

Фактическое количество вводится порциями или граммами готового блюда. Для граммов нужен известный готовый вес выбранной версии рецепта; если его нет, показываем объяснение и предлагаем ввод порциями. Пропуск не создаёт съеденные калории и не меняет плановое количество.

Плановое и фактическое КБЖУ отображаются отдельно.

## 7. Предметные правила, важные для frontend

- **Рецепт** — переиспользуемое описание блюда.
- **Версия рецепта** — определённый состав и выход. При редактировании рецепта сегодняшние ещё не съеденные и последующие записи автоматически получают новую версию, сохраняя количество порций. Прошлые записи и записи с фактом съеденного сохраняют старую версию. Для общего блюда достаточно факта хотя бы одного участника, чтобы сохранить версию всей записи. Дату «сегодня» определяет backend по часовому поясу семьи.
- **Запись плана** — рецепт на определённую дату и приём пищи с заданными порциями.
- **Запись дневника** — факт питания с реальным количеством и зафиксированными пищевыми значениями.
- Количество для участника задаётся порциями относительно выхода рецепта. Не используем неоднозначное поле доли без определения основы расчёта.
- При изменении выхода рецепта, например с 2 до 4 порций, одна запланированная порция остаётся одной порцией новой версии; её КБЖУ может измениться.
- В первой версии ингредиенты рецептов вводятся в граммах. Штуки, ложки и миллилитры требуют явных коэффициентов перевода и добавляются отдельно.
- Даты плана передаются как календарные даты `YYYY-MM-DD`. Не превращаем их автоматически в UTC-полночь.
- Для факта питания учитываем момент времени и часовой пояс. Преобразования дат централизуем.
- Повторение блюда на несколько дней создаёт отдельные записи расписания с независимыми датами и порциями; они следуют общему правилу обновления рецепта. Факты съеденного и пропуски при копировании не переносятся.
- Приготовление одной партии на несколько дней — будущий сценарий: объединять записи в одну большую готовку и показывать количество необходимых приготовлений.
- У пользователя не более одной активной семьи. После выхода и присоединения к другой сохраняются собственные рецепты, цели и личная история; общий план прежней семьи автоматически не переносится.
- Изменение или перенос записи плана не меняет уже съеденные количества и КБЖУ в дневнике.
- На этапе закупок сессия хранит снимок списка. Изменение плана вызывает уведомление и предложение обновить список; обновление выполняется явно, с сохранением уже отмеченных покупок.

Эти правила требуют поддержки API. Окончательные DTO определяются backend-контрактом, а не локальными предположениями компонентов.

## 8. Взаимодействие с API

```text
React + MUI → RTK Query → REST API (FastAPI / Python) → PostgreSQL
```

Бизнес-endpoint планируем под префиксом `/api/v1`. Адрес API задаём централизованно через конфигурацию, без адресов сервера в компонентах. Для локальной разработки согласуем Vite proxy или CORS на FastAPI в зависимости от способа подключения.

Один базовый `createApi` для backend. Endpoint отдельных областей подключаются через `injectEndpoints`. Для стандартных JSON-запросов используем `fetchBaseQuery`.

Поток изменения данных:

```text
Действие пользователя
  → RTK Query mutation
  → проверка и сохранение на backend
  → успешный ответ
  → инвалидация соответствующих тегов
  → повторная загрузка активных запросов
  → обновлённые данные и итоги на экране
```

Теги планируем по областям: рецепты, план, дневник. Ключи кеша должны учитывать значимые параметры: семью, период и пользователя, когда они участвуют в запросе. При завершении сессии очищаем кеш персональных данных.

Сохранение рецепта может изменить планы сразу нескольких недель. Инвалидируем карточку и списки рецептов, затронутые планы, dashboard и их производные итоги. Backend возвращает идентификаторы и новые revision обновлённых планов. Кеш дневника не переписываем новыми пищевыми значениями: съеденное сохраняет свой снимок. После смены активной семьи заново загружаем её контекст, сохраняя доступ к личной истории по прежним членствам.

RTK Query не нормализует автоматически одну сущность между всеми ответами API. Связанные экраны обновляем явной инвалидацией или контролируемым обновлением кеша.

В первой реализации после мутации получаем серверный результат без сложной оптимистической синхронизации. Позже оптимистические изменения добавляются для конкретных действий с откатом при ошибке.

Обрабатываем загрузку, пустой результат, ошибку валидации, потерю авторизации, сетевую ошибку и конфликт версии. При конфликте изменения плана не перезаписываем чужую работу автоматически.

Для защиты от повторных нажатий показываем состояние сохранения. Операции, где повтор создаёт дубликат, требуют согласованной с backend идемпотентности.

## 9. API-контракты и проверки

FastAPI формирует OpenAPI на основе описания маршрутов и схем Pydantic. Эту спецификацию используем как источник API-контрактов для frontend. Планируем получать её через `/openapi.json` и генерировать TypeScript-контракты и, при удобстве, RTK Query endpoint через `@rtk-query/codegen-openapi`.

```text
Маршруты FastAPI + схемы Pydantic
  → OpenAPI
  → TypeScript-контракты / RTK Query endpoint
  → frontend
```

- Сгенерированный код не редактируем вручную.
- Теги кеша и дополнительное поведение задаём в расширении API.
- ORM-модели backend не импортируем в frontend.
- API DTO и значения формы могут различаться: преобразование выполняется явно.
- TypeScript проверяет код при разработке, но не проверяет произвольные данные во время выполнения.
- Проверка формы улучшает UX; backend независимо проверяет данные и права доступа.

Zod проверяет ввод пользователя на клиенте, Pydantic — данные запросов на сервере. Python-модели нельзя напрямую импортировать в TypeScript. Клиентские формы согласуем с OpenAPI; генерация TypeScript-типов сама по себе не создаёт Zod-схемы и не заменяет проверку значений во время выполнения.

Формат ошибок API и преобразование серверных ошибок полей в ошибки React Hook Form согласуем с backend и реализуем в API-адаптерах слайсов. Чистые TypeScript-расчёты на клиенте дают предварительный результат; окончательные значения возвращает Python-backend.

### Будущий мобильный клиент

Тот же REST API должен обслуживать веб-приложение и будущий мобильный клиент. Язык backend не ограничивает выбор мобильной технологии. Авторизацию проектируем с учётом обоих типов клиентов; конкретный механизм определяем отдельно.

React Native + Expo обсуждался как вариант для мобильного приложения, но пока не выбран окончательно. При таком выборе можно переиспользовать API-контракты, Zod-схемы и чистые TypeScript-функции, если они не зависят от браузера. UI на MUI остаётся веб-интерфейсом; мобильные компоненты создаются отдельно.

### Подмена API через MSW в development

MSW (Mock Service Worker) — выбранный инструмент для подмены API в development. Он перехватывает HTTP-запросы и возвращает заранее описанные моковые ответы backend. В браузере используется Service Worker. Отдельный backend-процесс для таких ответов запускать не требуется.

Обработчики имитируют ответы FastAPI. При отключении подмены те же запросы RTK Query уходят на реальный backend.

```text
Без подмены: компонент → RTK Query → backend → ответ
С MSW:      компонент → RTK Query → обработчик MSW → тестовый ответ
```

Это позволяет разрабатывать экраны до готовности backend и воспроизводить пустые ответы, задержки, ошибки доступа и ошибки сервера. При необходимости те же обработчики можно использовать в тестах Vitest.

Правила использования:

- запуск и сборка обработчиков находятся в `app/mocks`;
- обработчики конкретной сущности могут находиться в её `api`-сегменте и экспортироваться через отдельную точку входа для mocks;
- обработчики уникального сценария теста задаются рядом с тестом;
- моковые ответы соответствуют API-контракту;
- RTK Query и UI не переключаются на отдельную реализацию запросов;
- включение в разработке задаётся явной настройкой, в production подмена отключена;
- не реализуем в обработчиках полноценный второй backend; необходимые изменения состояния имитируем минимально.

MSW не проверяет реальную реализацию backend. После подключения API отдельно проверяем совместную работу с сервером.

## 10. Проверка реализации

Тесты запускаем через Vitest. Для компонентных тестов предлагаем React Testing Library и DOM-окружение. Сквозные тесты не пишем.

Приоритет — сценарии с риском ошибочных данных:

- масштабирование КБЖУ по количеству порций;
- добавление и удаление ингредиентов в редакторе;
- корректный ввод дробных количеств;
- обновление плана и итогов после мутации;
- различие планового и фактического количества;
- сохранение истории после изменения рецепта;
- автоматическое обновление сегодняшних несъеденных и будущих записей после правки рецепта с сохранением количества порций;
- ввод съеденного в граммах при известном готовом весе, пропуск и незапланированная еда;
- ошибки сети, повторное сохранение и конфликт редактирования.

Основной сценарий для ручной приёмки: создать рецепт → добавить в план → изменить порции → отметить съеденное → проверить итоги дня. Его отдельные части проверяем модульными и компонентными тестами на Vitest.

Не нужны тесты, которые только повторяют внутреннюю структуру компонентов или проверяют стандартное поведение MUI.

## 11. Порядок реализации

1. Инициализировать React + TypeScript + Vite и базовую структуру FSD.
2. Подключить MUI, тему, маршрутизацию, Redux с RTK Query, React Hook Form, Zod, Vitest и MSW для development.
3. Реализовать поиск ингредиентов, каталог и редактор рецепта.
4. Реализовать расписание, добавление блюда и изменение порций.
5. Реализовать дневник и разделение плановых и фактических итогов.
6. Выполнить ручную приёмку основного сценария, проверить адаптацию под телефон и тесты Vitest.
7. Развивать семейный режим, покупки и ИИ отдельными этапами.
