# План реализации Food Tracker

Создан: 7 ноября 2026 года.

Цель первой версии: пользователь создаёт аккаунт, заводит продукты и блюда, составляет личный план, записывает съеденное, исправляет ошибки и сравнивает питание с целями КБЖУ.

Это рабочий план и журнал результатов. Предметные правила, API и границы MVP определены в [backend/README.md](backend/README.md); интерфейс и клиентские проверки — в [frontend/README.md](frontend/README.md). При изменении требований сначала обновляем соответствующий README, затем план.

## Как ведём работу и отчёты

Каждая задача проходит цикл **контракт API → backend и проверки → frontend и проверки → ручная приёмка на реальном backend**. Для инфраструктурных задач выполняем применимые шаги. Контракты проектируем по мере реализации сценариев.

Статусы блоков: `Не начат`, `В работе`, `Готов`. Блок готов, когда выполнены все его задачи и критерии приёмки. Зависимые проверки добавляем при появлении соответствующей функциональности: например, сохранность истории после исправления продукта проверяем при реализации дневника.

Завершённую задачу заменяем отчётом на том же месте, сохраняя ID и название. Не оставляем рядом вторую копию исходного задания. Обновляем статус блока в таблице и кратко сообщаем результат пользователю.

Формат завершённой задачи:

```text
- [x] 2.2 Создание и исправление продукта — выполнено ДД.ММ.ГГГГ.
  - Реализовано: краткое описание доступного пользователю поведения.
  - Проверено: выполненные проверки и их результат.
  - Осталось: нет в рамках задачи / конкретные ограничения и ID оставшихся задач.
```

Частично выполненная задача остаётся с `[ ]` и исходным объёмом. Под ней записываем `Прогресс` и `Осталось`, включая невыполненные проверки. Не закрываем задачу при готовности только backend, если она включает интерфейс. Новую работу вне исходного объёма оформляем отдельной задачей с новым ID; существующие ID не перенумеровываем.

Для каждого пользовательского сценария проверяем применимые состояния: загрузку, пустой результат, ошибки ввода, отсутствие доступа, сетевой сбой, повторную отправку и конфликт изменений. Проверки выполняем в рамках каждого блока. Браузерные E2E-тесты не добавляем.

## 0. Основа проекта

- [ ] 0.1 Сервер и база: инициализировать FastAPI, PostgreSQL, конфигурацию, миграции, окружение и lock-файл.
- [ ] 0.2 Клиент: инициализировать React + TypeScript + Vite, тему MUI, навигацию, необходимые слои FSD, store и общий API-слой; подключить backend.
- [ ] 0.3 Проверки и контракты: настроить серверные и клиентские инструменты проверки, MSW для согласованных контрактов и получение клиентских типов из OpenAPI. Зафиксировать команды локального запуска и проверок.

**Готово, когда:** проект запускается по инструкции, frontend обращается к backend, миграции применяются к пустой базе и базовые проверки проходят. Созданы только необходимые заготовки.

## 1. Аккаунт и авторизация

- [ ] 1.1 Регистрация: email и пароль, отправка и повторная отправка кода, подтверждение почты и вход после подтверждения; обработка неверного и истёкшего кода.
- [ ] 1.2 Вход и сессия: обычный вход, текущий пользователь, восстановление сессии после перезагрузки, обновление access и координация вкладок по серверному контракту.
- [ ] 1.3 Восстановление и выход: смена забытого пароля по коду с отзывом сеансов, последующий обычный вход, выход и очистка персонального кеша; обработка сетевой ошибки выхода.
- [ ] 1.4 Профиль: чтение и изменение предусмотренных настроек пользователя, включая базовый часовой пояс.
- [ ] 1.5 Отдельная приёмка auth: проверить сценарии, ограничения и защиту из раздела 17 backend README, включая запрет доступа до подтверждения почты и назначения ADMIN через публичный API.

**Готово, когда:** полный цикл аккаунта работает в интерфейсе; сессия корректно восстанавливается и завершается; личные данные другого пользователя недоступны. Почтовый адаптер подключён, в тестах используется подмена.

## 2. Продукты

- [ ] 2.1 Каталог и поиск: собственные и опубликованные продукты, загрузка частями, карточка, происхождение данных и пустой результат.
- [ ] 2.2 Создание и исправление продукта: общая форма, КБЖУ на 100 г, состояние продукта и предусмотренные дополнительные поля; исправление с сохранением ID и проверкой revision.
- [ ] 2.3 Архивирование: убрать собственный продукт из нового выбора, сохранив существующие ссылки по правилам backend.
- [ ] 2.4 Публикация: ADMIN публикует и снимает с публикации только собственные карточки через те же формы; USER не может публиковать, ADMIN не получает доступ к чужим личным карточкам.

**Готово, когда:** пользователь может наполнить и исправить личный каталог; новый продукт изначально личный; общий поиск и действия публикации соблюдают права доступа.

## 3. Блюда и рецепты

- [ ] 3.1 Создание блюда: название, инструкция, строки продуктов и граммовки, выход в порциях, необязательный готовый вес; предварительный расчёт и сохранённое серверное КБЖУ.
- [ ] 3.2 Каталог блюд: поиск с загрузкой частями, карточка, состав и КБЖУ на порцию.
- [ ] 3.3 Изменение и копирование: авторское редактирование сохраняет ID; «Создать на основе» создаёт самостоятельное блюдо с новым ID. Интерфейс объясняет последствия и обрабатывает конфликт revision.
- [ ] 3.4 Архивирование: убрать блюдо из обычного выбора, сохранив существующие ссылки.

**Готово, когда:** можно создать блюдо из продуктов, найти его, изменить или создать копию. Расчёты используют актуальные продукты; готовый вес определяет возможность ввода съеденного в граммах.

## 4. Личный план питания

- [ ] 4.1 План недели: выбрать неделю, добавить блюда по дням, времени и типу приёма пищи; указать порции и порядок. На компьютере — недельная сетка, на телефоне — выбранный день и список.
- [ ] 4.2 Изменение и копирование: редактировать плановое блюдо, время и порции; копировать записи на выбранные даты без факта съеденного.
- [ ] 4.3 Перенос, пропуск и удаление: переносить запись, в том числе между неделями, ставить и снимать пропуск, удалять запись отдельным действием. Перенос выполняется через форму; drag-and-drop отложен.
- [ ] 4.4 Плановые итоги: показывать КБЖУ запланированного отдельно от съеденного; защищать изменения revision отдельной записи.

**Готово, когда:** пользователь составляет и перестраивает личную неделю без семьи. Наступление времени плана не создаёт съеденное.

## 5. Подтверждение еды и дневник

- [ ] 5.1 Подтверждение блюда: явно сохранить фактические время, блюдо и количество; поддержать «Уже съел», порции и допустимые граммы. Атомарно создать пищевой снимок по текущим данным на момент подтверждения.
- [ ] 5.2 Дневник: показать подтверждённое питание по фактическим датам и серверные итоги; различать план и съеденное. Повторное подтверждение не дублирует еду и не обновляет её пищевую базу.
- [ ] 5.3 Сохранность факта: проверить, что изменения продуктов и рецептов не меняют подтверждённое питание, а перенос и пропуск плана сохраняют факт на его дате. Подтверждение задним числом использует текущую пищевую базу на момент сохранения.

**Готово, когда:** каждое подтверждённое блюдо учитывается ровно один раз; неподтверждённое не учитывается даже после времени плана и позднего открытия приложения. Исторические итоги читаются из снимков.

## 6. Незапланированная еда и быстрый ввод

- [ ] 6.1 Готовое блюдо без плана: выбрать блюдо, фактическое количество и время, сохранить съеденное одним действием и увидеть его в дневнике.
- [ ] 6.2 Быстрый ввод продукта: выбрать продукт, граммы и время без редактора рецепта; атомарно создать или переиспользовать простое блюдо и сохранить подтверждённую еду со снимком. Отделить простые блюда фильтром в каталоге.
- [ ] 6.3 Отсутствующий продукт: перейти из ввода еды к созданию продукта и вернуться с сохранением введённых данных; поддержать такой переход и из редактора обычного блюда.

**Готово, когда:** незапланированная еда сразу появляется в дневнике после сохранения, без дополнительного подтверждения и без записи в плане. Повтор отправки не создаёт двойное питание.

## 7. Исправление съеденного

- [ ] 7.1 Фактические данные: исправлять время, количество и фактически съеденное блюдо для запланированной и незапланированной еды. Изменение количества сохраняет базу снимка, замена фактического блюда получает новую базу по текущим данным.
- [ ] 7.2 КБЖУ отдельной записи: явно исправлять КБЖУ съеденного, масштабировать исправление при изменении количества и возвращать исходные значения снимка без чтения текущего каталога.
- [ ] 7.3 Ошибочная запись: отменить подтверждение запланированной еды с полным сбросом факта, снимка и исправлений; исправить или удалить незапланированную запись. Перед удалением или отменой объяснять последствия.

**Готово, когда:** исправления не создают дубликатов и не меняют другие записи; отменённое подтверждение не восстанавливается с течением времени. Изменение плана и изменение факта остаются отдельными действиями.

## 8. Цели КБЖУ и общие итоги

- [ ] 8.1 Периоды целей: создавать, изменять и удалять ошибочные периоды, включая прошлые; менять общую границу соседних периодов атомарно и показывать оба затронутых интервала.
- [ ] 8.2 Общий обзор: показывать план, съеденное и сравнение с целью для выбранных дат. Если цели нет, отображать её отсутствие.
- [ ] 8.3 История и свежесть: проверить сравнение после исправления прошлого периода, сохранность съеденного и политику кеша на N секунд при открытии, возвращении и восстановлении соединения, а также обновление после своих изменений.

**Готово, когда:** для даты используется действовавшая цель; периоды не пересекаются; правка цели меняет сравнение, сохраняя съеденное.

- [ ] 9.2 Выполнить предусмотренные проверки backend и frontend, проверить миграции на чистой базе, изоляцию пользователей, повторные запросы, конфликты и сохранность истории. Проверки отдельных блоков к этому моменту уже должны быть выполнены.

## Целевые user flow

Эти сценарии сохраняем как критерии приёмки, даже когда задачи выше заменены отчётами. Названия кнопок и компоновку уточняем при реализации без изменения предметных правил.

### F1. Первый запуск и возвращение

Регистрация → email и пароль → письмо с кодом → подтверждение → вход → личный экран с понятными действиями для пустого аккаунта.

Повторный вход: email и пароль → личный экран без нового кода. Перезагрузка восстанавливает сессию до персональных запросов. Восстановление пароля: email → код и новый пароль → отзыв сеансов → обычный вход. Выход очищает личные данные клиента.

**Результат:** аккаунт работает без семьи, готового каталога и заполненного плана.

### F2. Создать собственное блюдо

Блюда → создать → название → найти и добавить продукты → указать граммовки → задать выход и необязательный готовый вес → проверить КБЖУ → сохранить.

Если продукта нет: создать продукт → вернуться к составу с сохранёнными данными → продолжить создание блюда.

**Результат:** блюдо можно использовать в плане и дневнике. Изменение обновляет это блюдо, создание на основе сохраняет самостоятельную копию.

### F3. Запланировать и подтвердить еду

План → неделя и день → добавить блюдо → время и порции → сохранить. После еды: открыть карточку → подтвердить → проверить фактические время, блюдо и количество → сохранить → увидеть съеденное в дневнике.

**Результат:** план и факт различимы. План на 13:00 без подтверждения не становится съеденным при открытии в 15:00.

### F4. Быстро записать перекус

Добавить съеденное → продукт → найти йогурт → указать 150 г и время → сохранить съеденное → увидеть запись и итоги дневника.

Если продукта нет: создать его → вернуться к вводу еды → сохранить. Для готового блюда: выбрать блюдо вместо продукта → указать количество и время → сохранить.

**Результат:** еда записана одним сохранением, без ручного создания рецепта, второго подтверждения и изменения плана.

### F5. Изменить план и исправить факт

Подтвердить обед → перенести плановую карточку на другой день или изменить плановые порции → открыть дневник исходного дня.

**Результат:** съеденное остаётся на фактической дате с фактическим количеством. Чтобы исправить факт, пользователь отдельно открывает съеденное и меняет время, количество или блюдо. Ошибочное подтверждение scheduled можно отменить; ошибочную manual — исправить или удалить.

### F6. Исправить продукт и сохранить историю

Открыть собственный продукт → исправить КБЖУ → сохранить → посмотреть связанное блюдо и план → открыть ранее подтверждённую еду.

**Результат:** актуальные расчёты обновились, подтверждённая история сохранила свои значения. Для исправления истории пользователь отдельно меняет КБЖУ конкретной съеденной записи; возврат исходных значений использует её снимок.

### F7. Следить за целью

Цели → задать КБЖУ и дату начала → открыть день → увидеть план, съеденное и сравнение с целью → создать новую цель с другой даты → посмотреть обе даты.

**Результат:** каждая дата сравнивается со своей целью. Исправление прошлого периода меняет сравнение и сохраняет съеденное.

### F8. Пополнить общий каталог

ADMIN → создать собственный личный продукт → проверить карточку → опубликовать → другой пользователь находит продукт и использует его в блюде → ADMIN снимает публикацию.

**Результат:** продукт исчезает из нового выбора других пользователей; существующие ссылки продолжают работать. USER не может публиковать, ADMIN не получает доступа к чужим личным карточкам. Полный административный кабинет не требуется.
