# Food Tracker

Проект адаптивного приложения для личного планирования питания, дневника и расчётов КБЖУ. Репозиторий пока содержит проектную документацию: приложения, зависимости и миграции не созданы.

Актуальные продуктовые решения согласованы 7 ноября 2026 года.

## Порядок разработки

Разрабатываем по отдельным ручкам или небольшим связанным сценариям: **прото → backend → frontend**.

1. **Прото:** описываем и согласовываем контракт ручки — метод и маршрут, параметры, запрос, ответ и ошибки. В этом проекте «прото» означает контракт REST API в схемах Pydantic/OpenAPI. Контракт фиксируем до реализации бизнес-логики.
2. **Backend:** реализуем ручку по согласованному контракту и проверяем её работу и соответствие схемам.
3. **Frontend:** из OpenAPI получаем клиентские типы и подключаем интерфейс к готовой ручке backend.

Этот цикл повторяем для следующей ручки. Полностью проектировать все сущности и API заранее или ждать готовности всего backend для начала frontend не требуется: необходимые детали уточняем при согласовании очередного контракта. Если контракт нужно изменить, сначала согласовываем изменение, затем обновляем backend и frontend.

Основная разработка frontend идёт на реальном backend. MSW используем для тестов и воспроизведения отдельных состояний по уже согласованному контракту.

## Первая версия

- Личное недельное расписание без обязательного участия в семье: время, порции, копирование, перенос, пропуск и удаление.
- Продукты с КБЖУ, создаваемые прежде всего пользователями. Администратор использует тот же сценарий с другой меткой происхождения.
- Созданный продукт виден только автору; позднее автор может открыть его всем пользователям.
- Неизменяемые блюда с зафиксированными составом, выходом и КБЖУ. Изменение сохраняется как новое блюдо с новым ID, без версий.
- Быстрое добавление продукта в граммах через блюдо из одного ингредиента, без ручного заполнения редактора рецепта.
- Дневник с тремя способами учёта: автоматически, подтверждено пользователем, введено/скорректировано пользователем.
- Плановые и учтённые итоги, цели КБЖУ с редактируемыми периодами действия.

## Учёт питания

| Отметка | Правило |
|---|---|
| Учтено автоматически | Наступило время плана, пропуска и явного факта нет |
| Подтверждено пользователем | Пользователь явно подтвердил время, блюдо и количество |
| Введено или скорректировано пользователем | Пользователь добавил еду либо исправил фактические данные |

Происхождение записи scheduled/manual и способ учёта — разные свойства. Подтверждение и корректировка сохраняются отдельно: исправленная и затем подтверждённая еда учитывается один раз и сохраняет оба обстоятельства.

Автоматический вклад зависит от расписания: перенос обеда с 13:00 на 18:00 в 14:00 убирает его до 18:00. Явный факт имеет собственные время, блюдо и количество: перенос плана, смена плановых порций/блюда или пропуск сохраняют уже записанное съеденное. Факт исправляется отдельным действием. Можно записать, что блюдо съедено раньше запланированного.

Дневник и расписание используют одну MealEntry. Наступление времени не создаёт вторую запись; подтверждение и корректировка не добавляют повторные калории. Удаление всей записи исключает её факт. Полный сброс факта scheduled возвращает автоматические правила. Снятие подтверждения сохраняет ручные корректировки, а при их отсутствии полностью сбрасывает явный факт.

## Блюда и сохранность истории

Recipe — самостоятельное неизменяемое блюдо, RecipeItem — строки его состава со снимками КБЖУ. Рецепт и блюдо в документации обозначают одну сущность. Отдельных версий и переключения между ними в актуальной предметной модели нет.

«Создать на основе» открывает черновик и сохраняет новый Recipe. Новое блюдо не подменяет исходник в существующих планах, дневниках и у других пользователей. Архивирование скрывает старое блюдо из обычного выбора, сохраняя ссылки.

Исправление продукта пользователем или администратором не меняет уже сохранённые составы и историю. Записи питания ссылаются на неизменяемые блюда; полные копии состава в каждый приём не сохраняются.

При быстром добавлении используется single_product: одна строка на 100 г, одна техническая порция и готовый вес 100 г. Пользователь вводит граммы. Переиспользование такого блюда проверяет и источник, и снимок пищевых данных, чтобы исправленный продукт не получал старое КБЖУ.

## Два вида продуктов

| Сущность | Что представляет |
|---|---|
| Ingredient | Продукт, созданный пользователем или администратором: общий ингредиент либо описанный брендовый продукт |
| StoreProduct | Конкретную позицию реального каталога магазина с его внешним ID, упаковкой и характеристиками |

Пользователь и администратор создают Ingredient одним сценарием. Метка «создан пользователем» / «создан администратором» отражает тип создателя на момент создания. Видимость private/public независима от этой метки. Публикация открывает существующую карточку всем, сохраняя её ID и происхождение; обязательное одобрение администратором в MVP не вводится.

Общий поиск включает свои личные продукты и опубликованные карточки. После скрытия публичного продукта ранее созданные блюда сохраняют снимки, но это не открывает его личную исходную карточку. Для собственного питания публикация не требуется.

Карточка человека не считается реальным магазинным товаром лишь по похожему названию или метке администратора. Сопоставление с каталогами магазинов, выбор бренда/замен, актуальные цены и наличие развиваются отдельным этапом. Пользовательский продукт можно использовать без магазинной связи.

## Семья и дальнейшее развитие

Семья объединяет личные планы без копирования; личные данные сохраняются после выхода. Каждое вступление — отдельный период [joined_at, left_at), возврат создаёт новый период и не перезаписывает старый. Периоды пользователя не пересекаются, активная семья — не более одной.

Будущий семейный дневник учитывает доступное питание за периоды участия, включая бывших участников и исключая перерывы. Для автоматического учёта используется плановое время, для явного факта — фактическое. Перенос плана с явным фактом не меняет семейную принадлежность этого факта. Видимость семейной истории рассматривается отдельно от сохранения периодов.

После MVP: семейный интерфейс и история, шаблоны недель, закупки со снимками списка, запасы, объединение записей в готовку, магазины, подтверждаемый ввод по фото и прогнозирование.

Модель приготовления остаётся упрощённой: явно заданные состав и готовый выход без коэффициентов потерь. Сложные сценарии смены часовых поясов откладываются при сохранении базовых времени и пояса. Браузерные E2E-тесты не добавляются; проверки расчётов, интеграционные/компонентные проверки и ручная приёмка остаются.
