# Food Tracker

Проект адаптивного приложения для личного планирования питания, дневника и расчётов КБЖУ. Репозиторий пока содержит проектную документацию: приложения, зависимости и миграции не созданы.

Актуальные решения согласованы 7 ноября 2026 года.

## Документы и источник истины

- [backend/README.md](backend/README.md) — единый источник истины: скоуп MVP, будущие этапы, сущности, бизнес-правила, расчёты, доступ, API и серверная архитектура.
- [frontend/README.md](frontend/README.md) — клиентский стек, структура, интерфейс, состояние, подключение API и проверки UI. Предметные правила не дублируются: документ ссылается на backend.
- [IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md) — блоки реализации, задачи, целевые user flow и краткие отчёты о завершённых задачах.
- Корневой README описывает назначение репозитория, навигацию и общий порядок работы.

Изменение предметного правила сначала фиксируем в backend/README.md, затем обновляем зависимые ссылки и клиентское поведение. Границы первой версии и дальнейшее развитие описаны в [задачах и этапах](backend/README.md#1-задачи-и-этапы), критерии готовности — в [приёмке backend](backend/README.md#готовность-первой-версии).

## Порядок разработки

Разрабатываем по отдельным ручкам или небольшим связанным сценариям: **прото → backend → frontend**.

1. **Прото:** согласовываем метод и маршрут, параметры, запрос, ответ и ошибки. «Прото» означает контракт REST API в схемах Pydantic/OpenAPI; его фиксируем до бизнес-логики.
2. **Backend:** реализуем ручку, проверяем её работу и соответствие контракту.
3. **Frontend:** получаем клиентские типы из OpenAPI и подключаем интерфейс к готовой ручке.

Цикл повторяется для следующего сценария. Полностью проектировать все API заранее и ждать готовности всего backend не требуется. Изменение контракта сначала согласовываем, затем переносим в реализацию обеих частей.

Основная разработка frontend идёт на реальном backend. MSW используется для тестов и воспроизведения отдельных состояний по согласованному контракту. Авторизация реализуется и принимается отдельным блоком по [серверной спецификации](backend/README.md#17-авторизация-и-доступ).

Прогресс ведём в [плане реализации](IMPLEMENTATION_PLAN.md). После завершения каждой задачи заменяем её описание кратким отчётом: что реализовано, как проверено и что осталось. Частично выполненную задачу не отмечаем завершённой. Отчёт обновляем вместе с реализацией, а в ответе пользователю кратко сообщаем результат.
